# 심플 모드

심플 모드는 ReleaseDock의 두 번째 진입점입니다. 사용자는 Keycloak SSO로 로그인하고, 관리자가 미리 등록한 대상을 하나 고르고, `tar.gz`를 올리고, 실행 버튼을 누르고, 로그를 봅니다. 그게 전부입니다.

서버가 하는 일도 딱 두 가지입니다.

1. 업로드한 패키지를 대상에 지정된 디렉터리에 저장한다.
2. 지정된 명령 하나를 실행한다.

`docker load`, 이미지 태그, Harbor push, 승인, health check, 버전 비교는 **하지 않습니다**. 이미지 로드를 포함한 실제 배포 절차는 관리자가 등록한 명령(스크립트) 안에서 처리합니다. 애플리케이션·환경·배포 프로필·릴리즈 상태 머신도 사용하지 않으므로, 전체 모드의 Quick Deploy와는 완전히 분리된 경로입니다.

전체 모드(릴리즈 오케스트레이션)는 그대로 남아 있습니다. 두 모드는 같은 설치본에서 공존합니다.

---

## ⚠️ 보안 경계 — 반드시 읽으십시오

전체 모드의 배포 스크립트는 DB·암호화 키·container runtime 권한이 없는 별도 UID(`releasedock-executor`)에서 실행됩니다. **심플 모드는 이 격리를 사용하지 않습니다.** 명령은 API 서비스 계정(`releasedock`)이 직접 실행합니다.

따라서 다음이 성립합니다.

- **심플 대상에 등록하는 명령은 `releasedock` 계정의 권한으로 무엇이든 할 수 있습니다.** 명령 등록은 사실상 임의 코드 실행 권한을 주는 것과 같으므로, `admin.simple.write` 권한은 최소한의 인원에게만 부여하고 신뢰할 수 있는 스크립트만 등록하십시오.
- 명령 경로와 인자는 **관리자만** 지정할 수 있습니다. 사용자는 대상을 고르고 파일을 올릴 뿐이며, 경로나 명령을 입력할 수 있는 경로는 API에 존재하지 않습니다.
- 명령 등록·변경은 브라우저 세션에서만 가능합니다(API 키로는 불가). 실행은 일반 작업이므로 `simple.deploy` 범위의 개인 API 키로도 가능합니다.
- `releasedock-server.service`에 `NoNewPrivileges=true`가 설정되어 있으므로 **명령 안에서 `sudo`는 동작하지 않습니다.** 명령이 `docker load`를 해야 한다면 `releasedock` 계정이 docker 그룹에 속해야 하고, 이는 사실상 root 권한과 같습니다. 이 위험을 감수할 수 없다면 전체 모드의 Runner 경로를 사용하십시오.
- 업로드 경로는 `ProtectSystem=strict` + `ReadWritePaths` 때문에 `/var/lib/releasedock` 하위여야 합니다. 다른 위치를 쓰려면 `deploy/releasedock-server.service`의 `ReadWritePaths`도 함께 바꿔야 합니다.

명령 실행 자체는 전체 모드 executor와 동일한 가드를 사용합니다(`backend/internal/localexec`). 절대 경로의 실행 가능한 일반 파일만 허용하고, 셸을 거치지 않으며(`exec.CommandContext`에 인자 배열 전달), 환경변수는 allowlist만 넘기고, 제한 시간 초과 시 프로세스 그룹 전체를 SIGKILL로 정리합니다.

## 관리자 준비

### 1. 명령 지정 방식 선택

**관리 → 심플 모드 설정**(`/admin/settings/simple`)에서 두 가지 중 하나를 고릅니다.

| 방식 | 동작 | 언제 쓰나 |
| --- | --- | --- |
| **서비스별 명령** (`PER_TARGET`) | 심플 대상마다 등록된 명령을 각각 실행합니다. | 서비스마다 배포 스크립트가 다를 때 |
| **공통 명령 하나** (`SHARED`) | 모든 대상이 공통 명령 하나를 실행합니다. 대상 정보는 환경변수로 전달됩니다. | 범용 스크립트 하나가 인자·환경변수로 분기할 때 |

전환 규칙:

- `SHARED`로 바꾸려면 공통 명령이 먼저 유효하게 저장돼 있어야 합니다.
- `PER_TARGET`으로 바꾸려면 활성 대상 **전부**에 실행 명령이 설정돼 있어야 합니다.
- 모드를 바꿔도 대상의 개별 명령 값은 **삭제되지 않습니다.** `SHARED`에서는 읽지 않을 뿐이므로 언제든 되돌릴 수 있습니다.
- 실행 시점에 서버가 모드를 다시 읽어 명령을 결정합니다. 화면에 표시된 값이 아니라 실행 순간의 활성 설정이 기준입니다.
- 어떤 명령으로 실행됐는지는 실행 기록에 스냅샷으로 남으므로, 나중에 설정을 바꿔도 과거 이력은 흔들리지 않습니다.

같은 화면에서 **기본 화면 모드**(심플/전체)와 **업로드 루트**도 지정합니다.

### 2. 심플 대상 등록

**관리 → 심플 대상**(`/admin/simple-targets`)에서 등록합니다.

| 항목 | 설명 |
| --- | --- |
| 사용자 표시 이름 | 사용자가 목록에서 보게 될 이름. 예: `AI 포털 운영` |
| 업로드 경로 | 패키지를 저장할 절대 경로. 업로드 루트 하위여야 하며 심볼릭 링크는 거부됩니다. |
| 실행 명령 절대 경로 | 실행 가능한 일반 파일. `SHARED` 모드에서는 사용되지 않지만 값은 보존됩니다. |
| 명령 인자 | 한 줄에 하나. `{{artifact}}`는 업로드한 파일의 절대 경로로 치환됩니다. |
| 작업 디렉터리 | 비우면 업로드 경로에서 실행합니다. |
| 제한 시간 | 1~86400초. 초과하면 자식 프로세스까지 함께 종료합니다. |
| 최대 업로드 크기 | 기본 10 GiB |

`{{artifact}}` 치환은 인자 분리가 끝난 뒤에 일어납니다. 따라서 파일 경로에 공백이나 특수문자가 있어도 인자가 쪼개지거나 셸 구문이 되지 않습니다.

## 명령에 전달되는 환경변수

allowlist에 있는 값만 전달되며, 그 외 서버 환경변수는 상속되지 않습니다.

| 변수 | 값 |
| --- | --- |
| `ARTIFACT` | 업로드된 파일의 절대 경로 |
| `ARTIFACT_DIR` | 대상의 업로드 디렉터리 |
| `ARTIFACT_NAME` | 원본 파일 이름 |
| `ARTIFACT_SHA256` | 업로드 중 계산한 SHA-256 |
| `RELEASEDOCK_TARGET` | 심플 대상 이름 |
| `RELEASEDOCK_RUN_ID` | 실행 ID |
| `ACTOR` | 실행을 요청한 사용자 ID |
| `PATH` `HOME` `LANG` `LC_ALL` | 고정값 |

예시 스크립트:

```bash
#!/bin/bash
set -euo pipefail

echo "[$RELEASEDOCK_TARGET] $ARTIFACT_NAME ($ARTIFACT_SHA256)"
docker load --input "$ARTIFACT"
docker compose -f /opt/deploy/"$RELEASEDOCK_TARGET"/compose.yml up -d
```

## SSO 연동 (Redirect URI 설정 없이)

Keycloak 연동에 필요한 값은 **Issuer, Client ID, Client Secret** 세 가지입니다. Redirect URI는 입력하지 않아도 됩니다.

서버는 다음 순서로 Redirect URI를 결정합니다.

1. OIDC 설정에 Redirect URI가 명시되어 있으면 그 값
2. 없으면 일반 설정의 공개 HTTPS URL + `/api/v1/auth/oidc/callback`
3. 그것도 없으면 접속에 사용된 주소 + `/api/v1/auth/oidc/callback`

로그인 요청과 토큰 교환은 완전히 동일한 Redirect URI를 제시해야 하므로, 로그인 시점에 결정한 값을 state에 고정해 두고 콜백에서 그대로 재사용합니다. 따라서 두 요청이 서로 다른 호스트명으로 들어와도 교환이 깨지지 않습니다.

**Keycloak Client의 Valid redirect URIs에는 실제로 사용될 값을 등록해야 합니다.** 그 값은 관리 화면의 Keycloak OIDC 설정에 `Keycloak에 등록할 Redirect URI`로 표시되므로 그대로 복사하면 됩니다.

리버스 프록시를 쓰는 경우 파생 규칙은 아래를 따릅니다.

- 루프백이 아닌 호스트는 항상 `https`로 파생합니다. TLS를 종료하는 프록시가 `X-Forwarded-Proto`를 보내지 않아도 올바른 값이 나옵니다.
- `X-Forwarded-Proto`와 `X-Forwarded-Host`는 **관리자 접근 IP 설정의 신뢰 프록시 CIDR에 등록된 주소에서 온 요청에만** 반영합니다. 등록되지 않은 출처의 헤더는 무시하므로 클라이언트가 Redirect URI를 조작할 수 없습니다.
- 호스트가 여러 개이거나 특정 값을 강제해야 하면 Redirect URI를 직접 입력하십시오.

### 자동 로그인 (Keycloak 세션 재사용)

`Keycloak 세션이 있으면 자동 로그인` 을 켜면, 사이트에 접속했을 때 Keycloak 세션이 살아 있는 사용자는 로그인 화면을 보지 않고 바로 들어갑니다.

동작 방식은 OIDC 표준의 silent authentication 입니다. 인증 요청에 `prompt=none` 을 붙이므로 Keycloak 은 화면을 전혀 띄우지 않고 둘 중 하나로 답합니다.

- 세션이 살아 있으면 곧바로 code 를 돌려주고 로그인이 완료됩니다.
- 세션이 없으면 `login_required` 오류를 돌려주며, 사용자는 평소의 로그인 화면을 보게 됩니다.

iframe 을 쓰지 않고 최상위 리다이렉트로 처리하므로 서드파티 쿠키 차단의 영향을 받지 않습니다.

**무한 리다이렉트를 막는 장치**가 여러 겹 있습니다.

- 브라우저 세션당 **한 번만** 시도합니다 (`sessionStorage`). 새 탭에서는 다시 시도합니다.
- 세션이 없다는 응답을 받으면 `/login?sso=none` 으로 돌아오며, 이 표시가 있는 동안에는 재시도하지 않습니다.
- `sessionStorage` 를 쓸 수 없는 환경(시크릿 모드, 사이트 데이터 차단)에서는 **시도하지 않는 쪽으로** 실패합니다.

**사용자가 직접 로그아웃하면 자동 로그인이 멈춥니다.** Keycloak 세션이 남아 있어도 마찬가지입니다. 로그아웃했는데 즉시 다시 로그인되면 로그아웃이 동작하지 않는 것처럼 보이기 때문입니다. 다시 로그인하면 억제가 해제됩니다.

권한 오류(403)는 자동 로그인을 유발하지 않습니다. 세션은 정상이고 권한만 부족한 상황이므로 리다이렉트할 이유가 없습니다.

Keycloak Client 설정에서 별도로 켤 것은 없습니다. Valid redirect URIs 만 이미 맞게 등록되어 있으면 됩니다.

### token_endpoint is invalid 오류

이 오류는 Keycloak의 discovery 문서(`/.well-known/openid-configuration`)가 내려준 endpoint를 서버가 받아들일 수 없을 때 발생합니다. 오류 메시지에 문제가 된 endpoint 이름과 실제 값, 그리고 이유가 함께 표시됩니다.

먼저 Keycloak이 무엇을 내려주는지 확인하십시오.

```bash
curl -s https://keycloak.company.local/realms/company/.well-known/openid-configuration \
  | tr , '\n' | grep -E 'issuer|authorization_endpoint|token_endpoint|jwks_uri'
```

가장 흔한 원인은 **Keycloak이 backchannel URL을 내부 평문 HTTP로 내려주는 구성**입니다. Keycloak은 frontend URL(`authorization_endpoint`)과 backchannel URL(`token_endpoint`, `jwks_uri`)을 다르게 생성할 수 있어서, 앞단은 `https://`인데 `token_endpoint`만 `http://내부호스트:8080/...`으로 나오는 경우가 있습니다.

해결 방법은 두 가지입니다.

1. **권장** — Keycloak 쪽에서 고칩니다. `KC_HOSTNAME`을 공개 주소로 지정하고 `KC_HOSTNAME_BACKCHANNEL_DYNAMIC=false`로 두면 backchannel도 같은 HTTPS 주소를 사용합니다. 리버스 프록시 뒤라면 `KC_PROXY_HEADERS=xforwarded`도 함께 설정하십시오.
2. **폐쇄망에서 TLS가 없는 경우** — 관리 화면의 Keycloak OIDC 설정에서 `내부 평문 HTTP endpoint 허용`을 켭니다. Client Secret이 평문으로 전송되므로, 이 옵션을 켜도 서버는 **공개 라우팅 가능한 호스트에는 평문을 허용하지 않습니다.** 사설 IP(RFC1918/RFC4193), 루프백, 링크로컬, 점 없는 내부 이름과 `.local`·`.internal`·`.intranet` 도메인만 받아들입니다.

다른 원인들:

- `OIDC discovery issuer ... does not exactly match ...` — 설정한 Issuer 문자열이 Keycloak이 내려준 `issuer`와 **정확히** 일치해야 합니다. 뒤 슬래시나 호스트명 차이도 불일치입니다.
- `OIDC discovery token_endpoint is missing` — realm 경로가 틀렸거나 discovery 문서가 예상과 다릅니다.
- `OIDC discovery request: ...` — 네트워크나 TLS 신뢰 문제입니다. 사설 CA라면 서버의 트러스트 스토어에 CA를 설치해야 합니다.

## 사용자 흐름

1. Keycloak SSO로 로그인합니다.
2. 기본 모드가 심플이면 로그인 직후 **배포** 화면으로 이동합니다.
3. 배포 대상은 하나뿐이면 선택할 필요가 없습니다. 서버가 유일한 활성 대상을 자동으로 사용합니다. 대상이 여러 개일 때만 선택란이 나타납니다.
4. `.tar.gz`를 끌어 놓습니다. **여러 개를 한 번에 놓아도 됩니다.** 파일명 규칙은 없습니다.
5. **배포 실행**을 누르면 저장 후 명령이 실행되고 로그가 실시간으로 표시됩니다.

여러 개를 올린 경우 파일은 **순차적으로** 처리됩니다. 대상당 동시 실행이 1건으로 제한되어 있기 때문이며, 각 파일이 별도의 실행 기록과 로그를 남깁니다. 목록에서 파일별 상태를 확인할 수 있고 진행 중에 남은 파일을 중단할 수 있습니다.

같은 이름의 파일을 다시 올리면 원자적으로 덮어씁니다. 같은 패키지를 다시 배포하는 것이 정상 흐름이기 때문입니다.

배포되지 않은 파일이 목록에 남으면 **다시 시도** 버튼이 나타납니다. 중단한 파일(`건너뜀`), 업로드가 거부되거나 명령이 실패한 파일(`실패`·`시간 초과`), 상태를 확인하지 못한 파일(`확인 불가`)을 원래 순서 그대로 다시 대기 상태로 되돌리며, 이미 성공한 파일은 다시 올리지 않습니다. 파일은 브라우저에 남아 있으므로 다시 고를 필요가 없습니다. `확인 불가` 파일도 함께 되돌아가는데, 그 실행이 아직 진행 중이라면 대상당 동시 실행 1건 제약에 걸려 업로드가 거부되므로 같은 패키지가 두 번 배포되지는 않습니다. 실행이 끝난 뒤에는 목록의 어떤 항목이든 개별로 제거할 수 있습니다.

### 메뉴 제한

심플 모드에서는 메뉴가 **배포**와 **실행 기록**, 그리고 **내 프로필**만 노출됩니다. 릴리즈·대시보드·배포 프로필·Harbor·Runner 등 전체 모드의 화면은 보이지 않습니다. 관리 권한이 있는 사용자에게만 **관리** 섹션(심플 대상, 심플 모드 설정, 일반 설정, 관리자 접근 IP, 사용자, Keycloak OIDC, 감사 로그)이 추가로 보입니다.

두 모드를 모두 쓸 수 있는 사용자는 우측 상단 프로필 메뉴에서 모드를 전환할 수 있으며, 선택은 개인 설정으로 저장되어 다음 로그인에도 유지됩니다.

## Harbor 복제 규칙 자동 실행

심플 모드 설정에서 **Harbor Registry 와 복제 규칙을 하나 골라 두면, 배포 명령이 성공한 뒤 그 규칙을 자동으로 실행**합니다. 사용할지 여부는 같은 화면의 체크로 켜고 끕니다.

```text
업로드 → 명령 실행 → (exit 0) → Harbor 복제 트리거 → 완료 대기 → 앱 배포 명령 → 기록
```

### 설정

| 항목 | 설명 |
| --- | --- |
| 배포 성공 후 Harbor 복제 규칙 실행 | 사용 여부 체크 |
| Harbor Registry | **Harbor Registry** 화면에 등록된 레지스트리에서 선택 |
| 복제 규칙 | 선택한 Harbor 에서 규칙 목록을 읽어와 이름으로 선택 |
| 복제 완료 대기 제한 시간 | 기본 900초 |
| 복제 실행 범위 | `업로드당 한 번` (기본) 또는 `파일마다` |

규칙 목록은 저장된 Robot 계정으로 Harbor 의 `/api/v2.0/replication/policies` 를 조회해 채웁니다. 따라서 이 화면을 쓰려면 `admin.simple.read` 와 `admin.registries.read` 가 함께 필요합니다. Harbor 에 연결하지 못하면 사유를 그대로 보여주므로 Robot 권한이나 endpoint 문제를 바로 알 수 있습니다.

복제를 켜려면 레지스트리와 규칙이 **둘 다** 지정되어야 합니다. 하나만 고른 채로는 저장이 거부됩니다.

### 동작

- **명령이 실패하면 복제하지 않습니다.** 반쯤 적용된 상태를 다른 Harbor 로 미러링하지 않기 위해서입니다.
- 복제 진행 상황은 실행 로그에 `[replication]` 줄로 남고, 상태가 바뀔 때마다 성공/실패/전체 건수를 기록합니다.
- 완료될 때까지 기다리며, 제한 시간을 넘기면 `TIMEOUT` 으로 마감합니다.
- **복제가 실패하면 실행 기록 전체가 실패로 남습니다.** 배포는 됐지만 미러링이 안 된 상태를 초록색으로 보여주지 않기 위해서이며, 오류 메시지에 배포 명령 자체는 성공했음을 함께 적습니다.
- 실행 상세에 복제 상태와 Harbor execution ID 가 표시됩니다.
- 설정은 실행이 끝나는 시점에 읽습니다. 긴 배포 중에 규칙을 켜면 그 배포부터 적용되고, 끄면 즉시 반영됩니다.

Harbor 가 규칙을 접수했지만 execution ID 를 알려주지 않는 경우에는 상태를 추적하지 않고 그 사실을 로그에 남깁니다. 추적할 수 없는 것을 성공으로 단정하지 않기 위해서입니다.

### 여러 파일을 한 번에 올릴 때

파일 하나가 실행 하나이므로, 여러 개를 끌어다 놓으면 실행도 그 수만큼 생깁니다. **복제 실행 범위**가 이때 복제를 몇 번 할지 정합니다.

| 값 | 동작 |
| --- | --- |
| `업로드당 한 번` (기본) | 모든 파일의 업로드와 배포 명령이 끝난 뒤, **마지막 파일의 실행에서 복제를 한 번만** 실행합니다 |
| `파일마다` | 파일마다 배포 명령이 성공할 때마다 복제를 실행합니다 |

한 번 누른 업로드에 속한 실행들은 같은 묶음(batch)으로 표시되고, 마지막 실행에만 "이 묶음의 마지막"이라는 표시가 붙습니다. 실행은 대상당 하나씩 순차로 진행되므로 마지막 실행이 시작된 시점에는 앞선 파일의 배포 명령이 모두 끝나 있습니다. 복제를 건너뛴 실행은 상세 화면에 `건너뜀 (마지막 파일에서 실행)` 으로 남습니다.

묶음 정보는 실행이 만들어질 때 고정되며 이후 변경할 수 없습니다. 묶음을 알리지 않고 올린 파일(단일 업로드, 외부 API 클라이언트)은 그 자체가 마지막 실행으로 취급되므로 예전과 동일하게 동작합니다.

#### 마지막 파일이 배포되지 않은 경우

"이 묶음의 마지막" 표시는 파일을 올리는 시점에 붙으므로, 그 마지막 파일까지 가지 못한 업로드는 미뤄 둔 단계를 실행할 실행이 없는 채로 끝납니다. **남은 파일 중단**을 누른 경우, 마지막 파일의 업로드가 거부된 경우, 마지막 파일의 배포 명령이 실패한 경우가 여기에 해당합니다. 앞선 파일들은 성공으로 남지만 이미지는 아직 복제되지 않았고 앱도 교체되지 않은 상태입니다.

배포 화면은 이 상황을 감지해 경고를 띄웁니다. 앞선 실행 중 하나라도 단계를 `건너뜀` 으로 남겼는데 마지막 실행이 그 단계에 도달하지 못했으면, 남은 패키지를 다시 배포하라는 안내가 표시됩니다. 목록의 **다시 시도** 버튼이 바로 그 조치이며, 되돌린 패키지 중 마지막 것이 미뤄 둔 단계를 다시 넘겨받습니다. 마지막 실행이 복제를 시도했다가 실패한 경우는 그 실행 자체가 실패로 보고되므로 별도 경고를 띄우지 않습니다.

#### 중간 파일이 배포되지 않은 경우

마지막 파일까지 도달했더라도 **묶음 안의 다른 파일이 배포되지 않았다면 미뤄 둔 단계를 실행하지 않습니다.** `업로드당 한 번` 으로 미뤄 둔 단계는 파일 하나가 아니라 업로드 전체를 대상으로 동작합니다. 복제는 그 시점에 레지스트리에 있는 것을 미러링하고 앱 배포는 애플리케이션을 한 번 교체하므로, 중간 파일이 실패해 그 파일의 이미지가 적재되지 않은 채로 실행하면 일부만 갖춰진 업로드를 배포된 것으로 만들게 됩니다.

마지막 실행은 자신의 배포 명령이 끝난 뒤 같은 묶음의 다른 실행이 모두 성공했는지 확인합니다. 하나라도 성공이 아니면 복제와 앱 배포를 `건너뜀` 으로 남기고, **배포 명령이 성공했더라도 그 실행은 실패로 기록합니다.** 실행 로그에 `[replication]`·`[app-deploy]` 줄로 이유가 남습니다. 확인 자체가 실패하면(DB 를 읽지 못한 경우) 단계를 실행하지 않는 쪽을 택합니다. 실패한 파일을 고쳐 다시 올리면 그 업로드가 새 묶음이 되어 단계가 정상적으로 실행됩니다.

이 규칙은 미뤄 둔 단계에만 적용됩니다. `파일마다` 로 둔 단계는 자기 파일과 함께 이미 실행됐으므로 뒤늦은 실패로 되돌리지 않습니다.

## 앱 배포 명령

Harbor 복제 **다음** 단계로 명령을 하나 더 실행할 수 있습니다. 이 명령은 파일마다 실행되는 배포 명령과는 **별개**입니다. 배포 명령이 올라온 패키지 하나를 풀고 이미지를 적재한다면, 앱 배포 명령은 필요한 이미지가 모두 제자리에 간 뒤 애플리케이션을 실제로 교체하는 역할을 맡습니다.

```text
… → Harbor 복제 성공 → 앱 배포 명령 실행 → 완료 대기 → 기록
```

### 설정

| 항목 | 설명 |
| --- | --- |
| Harbor 복제 다음으로 앱 배포 명령 실행 | 사용 여부 체크 |
| 앱 배포 명령 | 절대 경로. 셸을 거치지 않고 그대로 실행합니다 |
| 앱 배포 명령 인자 | 한 줄에 하나씩. `{{artifact}}` 는 마지막으로 올린 패키지의 절대 경로로 치환됩니다 |
| 앱 배포 작업 디렉터리 | 비우면 대상의 업로드 경로 |
| 앱 배포 제한 시간 | 기본 600초 |
| 앱 배포 실행 범위 | `업로드당 한 번` (기본) 또는 `파일마다` |

명령을 비운 채로 사용 여부만 켜면 저장이 거부됩니다. 매 배포마다 실패할 설정을 저장해 두지 않기 위해서입니다.

### 동작

- **배포 명령이 실패하면 실행하지 않습니다.** 복제를 켠 경우 **복제가 실패해도 실행하지 않습니다.** 미러링되지 않은 이미지로 앱을 교체하지 않기 위해서입니다.
- 복제를 끄고 앱 배포만 켜도 됩니다. 이때는 배포 명령이 성공하면 바로 이어서 실행합니다.
- **복제를 `업로드당 한 번` 으로 두면 앱 배포도 마지막 파일까지 기다립니다.** 앱 배포 실행 범위를 `파일마다` 로 두어도 마찬가지입니다. 앞선 파일에서는 아직 아무것도 미러링되지 않았으므로, 그 시점의 앱 교체는 레지스트리에 없는 이미지로 교체하는 일이 되기 때문입니다. 이때 앞선 실행의 앱 배포 상태는 복제와 같이 `건너뜀 (마지막 파일에서 실행)` 으로 남습니다.
- 출력은 실행 로그에 그대로 남고, 단계 시작·종료는 `[app-deploy]` 줄로 표시됩니다.
- 명령에는 배포 명령과 같은 환경 변수(`ARTIFACT`, `ARTIFACT_DIR`, `ARTIFACT_NAME`, `ARTIFACT_SHA256`, `RELEASEDOCK_RUN_ID`, `RELEASEDOCK_TARGET`, `ACTOR`)가 전달되며, 단계 구분을 위해 `RELEASEDOCK_STAGE=app-deploy` 가 추가됩니다.
- **앱 배포가 실패하면 실행 기록 전체가 실패로 남습니다.** 오류 메시지에 배포 명령과 복제는 성공했음을 함께 적습니다.
- 실행 상세에 앱 배포 상태가 표시됩니다.
- 배포 명령과 마찬가지로 API 서비스 계정이 직접 실행합니다. 맨 위의 [보안 경계](#️-보안-경계--반드시-읽으십시오)가 그대로 적용됩니다.

### 설정을 읽지 못한 경우

배포 후 단계 설정은 명령이 끝난 뒤에 읽습니다. 긴 배포 중에 켠 단계도 적용하고, 그 사이에 끈 단계는 실행하지 않기 위해서입니다. 이때 DB 를 읽지 못하면 복제와 앱 배포를 켜 두었는지조차 알 수 없으므로, **배포 명령이 성공했더라도 실행 기록은 실패로 남습니다.** 오류 메시지와 실행 로그의 `[post-deploy]` 줄에 배포 명령 자체는 성공했다는 사실과 읽지 못한 이유를 함께 적습니다. 단계가 실제로 필요했는지 확인한 뒤 다시 배포하십시오.

## 실행 이력과 로그

**실행 기록**(`/simple/runs`)에서 행을 누르면 **실행 상세**로 이동합니다. 여기서 그 실행의 전체 로그를 봅니다. 이미 끝난 실행도 저장된 출력을 그대로 다시 읽을 수 있고, 아직 진행 중이면 마지막으로 읽은 줄 다음부터 실시간으로 이어 붙입니다.

실행 상세에는 다음이 함께 표시됩니다.

- 상태, 종료 코드, 실패 사유, 소요 시간
- 배포 대상, 실행자, 원본 파일명, 크기, SHA-256, 저장 경로
- **그 실행이 실제로 사용한 명령** — 명령 방식(서비스별/공통), 실행 파일 경로, 인자, 제한 시간. 실행 시점의 스냅샷이므로 이후 설정을 바꿔도 과거 이력은 그대로입니다.

로그는 `로그 내려받기` 로 평문 파일로 받을 수 있습니다. `stderr` 줄에는 `[stderr]` 접두어가 붙습니다.

### 누가 무엇을 볼 수 있나

| 권한 | 볼 수 있는 범위 |
| --- | --- |
| `simple.read` | **자신이 실행한 기록과 로그만** |
| `admin.simple.read` | **모든 사용자의 실행 기록과 로그**. 목록에서 `전체 사용자` / `내 실행만` 을 전환할 수 있습니다 |

다른 사람의 실행에 접근하면 403 이 아니라 404 를 반환합니다. 실행 ID 의 존재 여부를 알려주지 않기 위해서입니다.

개인 API 키는 자신에게 부여된 scope 안에서만 동작하므로, `admin.simple.read` 를 가진 사용자라도 그 권한이 빠진 키로는 다른 사람의 실행을 읽을 수 없습니다.

> **v0.3.4 이하에서 올라오는 경우**: 이전에는 `simple.read` 만 있으면 모든 사용자의 실행 목록이 보였습니다. 이제 관리 권한이 없는 사용자에게는 본인 기록만 보입니다.

## 동시성과 복구

- 대상 하나당 동시에 실행되는 작업은 1건입니다(DB 부분 유니크 인덱스로 강제). 두 번째 요청은 `409`로 거부됩니다.
- 업로드한 파일은 임시 이름으로 먼저 저장하고, 실행 기록이 만들어져 대상을 확보한 뒤에야 원래 이름으로 확정합니다. 위 `409`처럼 **거부된 업로드는 대상 디렉터리의 파일을 건드리지 않습니다.** 같은 이름의 패키지를 다시 올리는 것은 정상적인 재배포이지만, 그 이름이 지금 실행 중인 명령이 읽고 있는 파일일 수 있기 때문입니다.
- 프로세스 전체 동시 실행은 4건으로 제한됩니다.
- 실행 로그는 작업당 8 MiB까지 저장합니다. 한도에 도달해도 명령은 계속 실행되고, 저장만 멈춥니다.
- 서버가 직접 남기는 진행 줄(`exit=...`, `[replication]`, `[app-deploy]`, `[post-deploy]`)은 명령 출력과 별개로 64 KiB 예산을 따로 씁니다. 명령이 8 MiB를 채워도 실행이 어떻게 끝났는지는 로그에 남습니다.
- 서버가 재시작되면 자식 프로세스도 함께 사라지므로, 부팅 시 `PENDING`/`RUNNING`으로 남은 작업을 `FAILED`로 마감합니다. 대상이 영구히 잠기지 않습니다.
- 종료 상태(`SUCCESS`/`FAILED`/`TIMEOUT`)에 도달한 실행 기록은 DB 트리거로 불변입니다.
- 배포 화면은 실행 상태를 1.5초마다 다시 읽습니다. 로그인이 만료됐거나(`401`/`403`) 실행 기록이 없으면(`404`) 즉시, 그 밖의 실패는 약 60초를 재시도한 뒤 확인을 중단합니다. 해당 파일은 성공도 실패도 아닌 `확인 불가` 로 표시되고, 남은 파일은 대기 상태로 남습니다. 배포 자체는 계속 진행 중일 수 있으므로 **실행 목록**에서 결과를 확인하십시오. (읽기 실패를 무한히 재시도하면 화면이 영구히 잠기고 남은 파일이 올라가지 않습니다.)

## 사용자 가이드 게시판

관리자가 가이드·공지·FAQ 게시글을 작성하면 사용자 화면의 **사용자 가이드** 메뉴에 표시됩니다. 심플 모드와 전체 모드 양쪽 메뉴에 나옵니다.

### 관리

**관리 → 가이드 게시판**(`/admin/guides`)에서 게시글을 등록·수정·삭제합니다.

| 항목 | 설명 |
| --- | --- |
| 제목 | 1~200자 |
| 분류 | 가이드 / 공지 / 자주 묻는 질문 |
| 요약 | 목록에 함께 표시됩니다. 500자까지 |
| 본문 | Markdown 일부 지원 |
| 상단 고정 | 목록 맨 위로 올립니다 |
| 정렬 순서 | 작은 값이 먼저. 읽는 순서를 정할 때 씁니다 |
| 공개 | 끄면 사용자 화면에 표시되지 않습니다 (초안) |

목록 순서는 **상단 고정 → 정렬 순서 → 최신순**입니다.

### 본문 서식

지원하는 문법은 아래와 같습니다.

```text
# 제목        ## 소제목        ### 작은 제목
- 목록        1. 번호 목록
> 인용        ---  구분선
**굵게**      `코드`
```  코드블록 (세 개의 백틱으로 감쌉니다)
```

**HTML 은 해석하지 않습니다.** 본문은 React 요소로 조립되며 어떤 경우에도 마크업으로 삽입되지 않으므로, 게시글을 통한 스크립트 주입이 불가능합니다. `<script>` 를 적으면 그 글자가 그대로 보입니다.

### 권한

| 권한 | 범위 |
| --- | --- |
| `guides.read` | 공개된 게시글 열람. 기본 제공 역할 전체에 부여됩니다 |
| `admin.guides.read` | 초안을 포함한 전체 목록 조회 |
| `admin.guides.write` | 등록·수정·삭제 |

설치 시 **심플 모드로 배포하기** 가이드가 하나 들어 있습니다. 수정하거나 지워도 다음 업그레이드에서 되살아나지 않습니다.

## 관리자 접근 IP 제한

**관리 → 관리자 접근 IP**(`/admin/settings/network`)에서 관리 기능을 사용할 수 있는 출발지 IP를 제한합니다. `/api/v1/admin/` 이하의 모든 관리 API와 `admin.` 권한을 요구하는 요청에 적용되며, 일반 사용자의 배포·조회에는 영향을 주지 않습니다.

- 허용 목록에는 단일 주소(`10.1.2.3`)와 대역(`192.168.10.0/24`)을 모두 쓸 수 있습니다.
- **리버스 프록시를 쓴다면 신뢰 프록시 CIDR을 반드시 입력하십시오.** 비워 두면 모든 접속이 프록시 IP로 보여 제한이 의미를 잃습니다. 여기에 등록된 주소에서 온 요청에 한해 `X-Forwarded-For`를 신뢰하며, 그때도 오른쪽에서부터 신뢰 프록시가 아닌 첫 주소만 채택합니다. 왼쪽 항목은 클라이언트가 임의로 넣을 수 있으므로 신뢰하지 않습니다.
- 자기 자신을 잠그는 저장은 거부됩니다. 현재 접속 IP가 새 허용 목록에 없으면 `409`로 실패하며, 화면에 현재 IP와 "목록에 추가" 버튼이 표시됩니다.
- 루프백(`127.0.0.1`, `::1`)은 서버 콘솔 복구를 위해 항상 허용됩니다.
- 화면 상단에 서버가 인식한 **현재 접속 IP**와, 프록시가 앞단에 있는 경우 **직접 접속 지점(프록시 주소)**을 함께 표시합니다. `X-Forwarded-For`가 있는데 그 프록시가 신뢰 목록에 없으면 경고와 함께 `프록시 신뢰 등록` 버튼을 제공하므로, 등록 후 저장하면 실제 클라이언트 IP가 표시됩니다.
- `목록에 추가` 버튼으로 현재 접속 IP를 허용 목록에 바로 넣을 수 있습니다.
- 차단된 시도는 감사 로그에 `admin.network.denied`로 남습니다.
- DB를 읽지 못하면 제한을 적용하지 않습니다. 일시적인 DB 장애가 모든 관리자를 잠그는 것을 막기 위해서입니다.
